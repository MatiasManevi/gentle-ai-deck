01 · Generative AI

What is an LLM: prediction, not thinking

A Large Language Model is a neural network with billions of parameters trained to predict the next token. It doesn't "think": it completes statistical patterns. The quality of the output depends on the quality of the context you give it.

02 · Generative AI

What an LLM is NOT

It's not a database, it doesn't learn from your conversations, it doesn't understand like a human, it's not deterministic. If you don't know this, you'll have incorrect expectations and constant frustration.

03 · Chat vs Agent

Chat responds text. Agent acts.

A chat generates text. An agent reads your code, edits files, runs tests and saves learning. It's the difference between asking someone for advice and having a pair-programmer with access to your project.

04 · Context Window

The fixed-size whiteboard

The context is everything the model "sees": system prompt, history, files read, your instruction. The context window is the physical size of that whiteboard, measured in tokens.

05 · Context Window

Attention decay: more is not better

A medida que llenas la ventana, el modelo no falla: degrada. Instruction drift, sesgo de recencia, codigo generico. Es sutil y peligroso porque el output "parece" correcto.

06 · Context Window

Compaction: forced amnesia

When the board fills up, the system generates a compressed summary and deletes the original messages. You lose variable names, design decisions, user preferences.

07 · Context Window

How the industry addresses it

Long context (1M+ tokens), RAG, fine-youning, memory layers, vector stores. Cada approach tiene tradeoffs: costo, latencia, precision, complejidad. Nadie lo resolvio del todo.

08 · 1st Context Evolution

It all started with AGENTS.md

The first idea: a giant markdown file with ALL the project rules. Style, patterns, anti-patterns, conventions, workflows. The agent read it at the start and "knew" how to work.

09 · 1st Context Evolution

AGENTS.md grows infinitely

Each new convention bloated the file. In real projects it can reach thousands of lines. It eats up the context window before you write your first prompt.

10 · 1st Context Evolution

First evolution: Skills

En vez de un archivo gigante, un router (AGENTS.md liviano) que apunta a SKILL.md especificos. Solo se carga el contexto que necesitas para la tarea acyoual. Contexto dinamico bajo demanda.

11 · 1st Context Evolution

One agent that does everything: why it degrades

"Analyze, design, test, and implement." Single agent fills its context to 80% before writing the first line of code. It compiles but ignores the decisions from step 1.

12 · 2nd Context Evolution

Second evolution: sub-agents

Skills resolve WHAT context to load. But a single agent still accumulates noise. The solution: delegate each phase to an ephemeral sub-agent with fresh context. It spawns, executes, reports, and dies.

El orquestador no trabaja: coordina. Delega cada tarea a un sub-agente especializado que recibe solo lo que necesita. Maxima precision, cero ruido acumulado.

13 · 2nd Context Evolution

Fresh context: starting clean

Cada sub-agente nace con la pizarra vacia. Solo recibe las instrucciones de su fase. No arrastra ruido de fases anteriores. Esa es la ventaja arquitectonica clave.

14 · SDD Orchestrator

The philosophy: engineering applied to AI

Instead of "ask and pray," we structure the work on an assembly line of experts. Spec-Driven Development applies software engineering principles to the AI workflow.

15 · SDD Orchestrator

Specialized roles

Explorer (reads code), Proposer (defines what), Spec Writer (requirements), Designer (architecture), Task Planner (splits work), Implementer (writes code), Verifier (validates quality).

16 · SDD Orchestrator

Real example: creating users endpoint

/sdd:new → Explorer detects stack → Proposer defines scope → Spec + Design run in paralell → Tasks divides the design in 4 tasks → Implementer generates code → Verifier validates against specs.

17 · Engram

Compaction kills decisions

You work 2 hours defining architecture. The system compacts. The agent no longer remembers you decided to use Clean Architecture with DI. It generates generic code.

18 · Engram

Engram: save signals, not everything

Engram does not save everything (that's noise). It save signals: decisions, resolved errors, patterns. Structured observations with What/Why/Where/Learned.

19 · Engram

Engram Architecture

One binary. No external dependencies. SQLite with Full-Text Search 5. Connects via MCP to 12 agents: Claude Code, OpenCode, Kilo Code, Gemini CLI, Cursor, VS Code Copilot, Codex, Windsurf, Antigravity, Kimi Code, Qwen Code, Kiro IDE — and any MCP-compatible agent.

20 · Engram

Progressive disclosure: 3 efficiency layers

Instead of dumping everything in context, Engram reveals information progressively. The agent decides how deep to go based on what it needs. Minimum tokens, maximum precision. 3 layers: mem_search (compact: titles + snippets), mem_context/timeline (session context), and mem_get_observation (full content untruncated).

21 · Engram

Las herramientas de memoria

The 5 critical tools. mem_current_project (new) confirms which project receives your saves before writing. And mem_save now only captures the associated prompt — you don't need to call mem_save_prompt explicitly.

22 · Engram

El Engram Loop: dos sesiones

Session 1: design → mem_save. Session 2: implement → mem_search retrieves decision → consistent code. Without Engram session 2 ignores session 1. With Engram there's real continuity.

23 · Engram

Dos formas de sincronizar: git o Cloud

Two valid sync paths, both work for solo and team. Git sync uses your existing repo, no extra infra, async (commit-based). Engram Cloud is a self-hosted server with web dashboard, real-time autosync, multi-user with roles. You choose based on your need: simplicity or visibility.

24 · Engram

Cloud mode: el mismo binario engram, multi-máquina y real-time

Cloud is not a separate product — it's a MODE of the same engram binary. You go from local SQLite to Postgres + server with engram cloud serve. Add web dashboard (templ + htmx), background autosync with exponential backoff, JWT auth + roles. 100% self-hosted — your hardware, your data, no telemetry.

25 · Engram

Engram vs alternativas: por que lightweight gana

No server, no embeddings, no cloud infra. A local binary that works offline. For teams just starting, simplicity is the most important feature.

26 · Skills Registry

El problema del prompt gigante

If you put all the rules in the system prompt, you fill the window before you start. The agent ignores rules and generates generic code. We already saw why in the evolution module.

27 · Skills Registry

AGENTS.md router + SKILL.md modulo

AGENTS.md as a lightweight index that maps intents to skills. Each SKILL.md has patterns, anti-patterns, and templates. Only what you need is loaded.

28 · Skills Registry

skill-creator: el equipo enseña al agente

Institutional knowledge is held by the team. With skill-creator each person creates their own skills: conventions, patterns, checklists. The agent learns from the real team. And the contextual loading directive makes the agent automatically load relevant skills when detecting triggers — no more "I forgot to use skill X."

29 · Skills Registry

Contexyoual skill loading: orchestrator resuelve, sub-agents consumen

The orchestrator reads the skill-registry ONCE at session start and caches the compact rules. For each delegation, it matches triggers (file context + task context) and injects the pre-digested rules into the sub-agent's prompt. Sub-agents do NOT read SKILL.md or the registry — they receive everything pre-resolved. Compaction-safe: if the cache is lost, the next delegation re-reads the registry.

30 · Stack & Libraries

Ecosistema: Engram + SDD + Skills

Engram da continuidad, SDD da estrucyoura, Skills da consistencia. Juntas resuelven los tres problemas del LLM: amnesia, degradacion y genericidad.

31 · Stack & Libraries

The Goodies

Speed ​​through automation. Consistency through skills. Quality through verification against specifications. Efficiency in memory and context window usage.

33 · Closing

Conclusion

Gentle-AI stands out as a powerful ecosystem configurator that empowers developers to transcend simple chat interactions and adopt a robust, production-ready AI workflow. By integrating persistent memory, spec-driven development, and efficient sub-agent orchestration, it significantly enhances the productivity and reliability of existing AI agents.

While Gentle-AI offers a unique and streamlined experience, it is part of a growing landscape of sophisticated orchestration frameworks, each catering to different architectural needs and developer preferences.
